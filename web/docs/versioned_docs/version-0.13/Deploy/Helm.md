# Helm and Kubernetes

Deploy Marmot to a Kubernetes cluster with the official Helm chart.

import { Steps, Step, Tabs, TabPanel, TipBox } from '@site/src/components/Steps';

## Install

<Steps>
  <Step title="Add the Helm repository">

```bash
helm repo add marmotdata https://marmotdata.github.io/charts
helm repo update
```

  </Step>
  <Step title="Install Marmot">

```bash
helm install marmot marmotdata/marmot
```

  </Step>
  <Step title="Sign in">

Forward the port to your machine:

```bash
kubectl port-forward svc/marmot 8080:8080
```

Open [http://localhost:8080](http://localhost:8080) and sign in as `admin` with the password `admin`. Marmot asks you to choose a new password straight away.

  </Step>
</Steps>

## Database

Marmot needs PostgreSQL. Use one of these:

<Tabs items={[
{ label: "Your own PostgreSQL", value: "external" },
{ label: "Embedded PostgreSQL", value: "embedded" },
{ label: "CloudNativePG", value: "cnpg" }
]}>
<TabPanel>

Connect Marmot to your existing PostgreSQL database:

```yaml
config:
  database:
    host: postgres.example.com
    port: 5432
    user: marmot
    passwordSecretRef:
      name: marmot-db-secret
      key: password
    name: marmot
    sslmode: require
```

  </TabPanel>
  <TabPanel>

For development and testing, turn on the embedded PostgreSQL:

```bash
helm install marmot marmotdata/marmot \
  --set postgresql.enabled=true
```

The chart generates a PostgreSQL password Secret named `<release>-postgresql`
with a `password` key and reuses it on upgrades. To use an existing Secret:

```yaml
postgresql:
  auth:
    existingSecret: marmot-postgres-credentials
    passwordKey: password
```

  </TabPanel>
  <TabPanel>

For production, [CloudNativePG](https://cloudnative-pg.io/) runs PostgreSQL with automatic failover, read replicas and connection pooling.

<Steps>
  <Step title="Install the CloudNativePG operator">

Install the operator with the [CloudNativePG installation guide](https://cloudnative-pg.io/documentation/current/installation_upgrade/), or apply its release manifest:

```bash
kubectl apply --server-side -f \
  https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/main/releases/cnpg-1.25.1.yaml
```

  </Step>
  <Step title="Configure and install Marmot with CNPG">

```yaml
# values.yaml
cnpg:
  enabled: true
  instances: 3  # 1 primary + 2 read replicas
  password: "<database-password>"

  parameters:
    shared_buffers: "256MB"
    work_mem: "64MB"
    effective_cache_size: "1GB"

  persistence:
    size: "10Gi"

  pooler:
    enabled: true
    instances: 2
    poolMode: "transaction"
```

```bash
helm install marmot marmotdata/marmot -f values.yaml
```

  </Step>
  <Step title="Verify the cluster is ready">

```bash
kubectl get clusters
kubectl get pods -l cnpg.io/cluster=marmot-cnpg
```

Every pod shows `Running`, and the primary's name ends in `-1`.

  </Step>
</Steps>

  </TabPanel>
</Tabs>

## Encryption key

Marmot encrypts the credentials it stores with this key, so every install needs one.

<Tabs items={[
{ label: "Generated by the chart", value: "auto" },
{ label: "Your own key", value: "custom" },
{ label: "None (development only)", value: "disable" }
]}>
<TabPanel>

By default the chart generates a key and stores it in a Secret:

```yaml
config:
  server:
    autoGenerateEncryptionKey: true
```

<TipBox variant="warning" title="Back up the generated key">
If the Secret is deleted, Marmot can't read the credentials it stored. Back the key up as soon as you install.
</TipBox>

For a release named `marmot`, the Secret is `marmot-encryption-key`:

```bash
kubectl get secret marmot-encryption-key \
  -o jsonpath='{.data.encryption-key}' | base64 -d
```

  </TabPanel>
  <TabPanel>

<Steps>
  <Step title="Generate an encryption key">

```bash
marmot generate-encryption-key
# or
openssl rand -base64 32
```

  </Step>
  <Step title="Create a Kubernetes secret">

```bash
kubectl create secret generic marmot-encryption \
  --from-literal=encryption-key="<encryption-key>"
```

  </Step>
  <Step title="Configure the Helm chart">

```yaml
config:
  server:
    autoGenerateEncryptionKey: false
    encryptionKeySecretRef:
      name: marmot-encryption
      key: encryption-key
```

  </Step>
</Steps>

  </TabPanel>
  <TabPanel>

For local development only, Marmot can run without a key and store credentials unencrypted:

```yaml
config:
  server:
    autoGenerateEncryptionKey: false
    allow_unencrypted: true
```

<TipBox variant="danger" title="Development only">
Every stored credential would be readable by anyone with access to the database. Never use this in production.
</TipBox>

  </TabPanel>
</Tabs>

## Serving plugins

To let plugins that run in your own networks answer data queries, turn on the serve listener. It needs an encryption key.

```yaml
config:
  query:
    serve:
      enabled: true
serveService:
  type: LoadBalancer
```

The chart opens port 8443, creates a separate `<release>-serve` Service for it and tells each replica the address its peers forward queries to. Expose the Service with a TCP load balancer or TLS passthrough, never one that terminates TLS. See [serve queries from your network](../Configure/serving-plugins.md).
